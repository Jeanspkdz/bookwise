# Book cover delivery benchmark

Date: 2026-11-19

## Question

Does loading a book cover directly from UploadThing (`<img src="...">`) perform better than fetching a 277 px WebP generated by IPX (the URL path used by `NuxtImg` when IPX is enabled)?

## Method

- Used the same public UploadThing cover URL in every sample.
- Direct path: Node `fetch()` of the original image with request caching disabled.
- IPX path: the installed `ipx` 4.1.0 / Sharp pipeline fetched that same URL, resized it to 277 px wide, and encoded it as WebP.
- Ran nine sequential paired samples. The order alternated for the last six pairs to reduce order bias.
- Timed the complete request or transformation in milliseconds and recorded the returned size.

This is a controlled **asset-path** comparison, not a full browser-page A/B test. The direct path corresponds to the URL used by a native `<img>` and by the current pass-through `NuxtImg`. The IPX path represents the remote fetch and transform requested by the previous IPX setup.

## Results

| Pair | Direct original (ms) | IPX resize + WebP (ms) | Order |
| ---: | ---: | ---: | --- |
| 1 | 3,645 | 10,498 | Direct, IPX |
| 2 | 8,781 | 2,200 | Direct, IPX |
| 3 | 1,196 | 1,072 | Direct, IPX |
| 4 | 1,122 | 1,588 | Direct, IPX |
| 5 | 542 | 689 | IPX, direct |
| 6 | 741 | 605 | Direct, IPX |
| 7 | 609 | 496 | IPX, direct |
| 8 | 848 | 498 | Direct, IPX |
| 9 | 479 | 581 | IPX, direct |
| **Median** | **848** | **689** | — |

The direct response was a **91,081 byte PNG**. IPX returned a **17,054 byte WebP**, an **81.3% reduction** in payload size.

## Interpretation

- IPX was about **159 ms faster at the median** in these samples, and returned a much smaller file. The measurements do not support the claim that IPX is inherently slower.
- Timings varied widely for both paths. In the first pair, IPX took 10.5 s; in another pair, the direct request took 8.8 s. This points to variable latency fetching the remote source as a major contributor. IPX adds an extra server fetch and transformation, but the fetch latency dominates and varies between requests.
- The initial dev-server screenshots showed IPX image requests taking roughly 2–8 s. Those screenshots are consistent with cold or slow source fetches, but they do not isolate the IPX overhead.
- The previous three-second delay inside `GET /api/book` delayed when the page learned which covers to load. It was separate from image request time and has since been removed.

## Limits

This benchmark did not measure a complete browser page under identical cold-cache and warm-cache conditions. It does not include browser scheduling, layout, decoding, Nitro's HTTP response layer, or the production CDN cache for transformed files. IPX was measured through its processing API, so its timing excludes the extra local HTTP hop from the browser to Nitro. Results are for one PNG cover and one network path; other covers and user locations may differ.

## Conclusion

The evidence shows a tradeoff: direct delivery avoids IPX's server-side fetch and transform, while IPX produced a file about five times smaller and had a slightly lower median in this run. A production decision should use a browser-level A/B measurement with identical images, cache state, viewport, and connection. No application code was changed as part of this benchmark.
